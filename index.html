Godot TPS Multiplayer Template

A commercial-grade, client-server multiplayer template for third-person shooters, built with Godot 4.6. Includes a dedicated server project, authoritative hit validation, transform snapshot interpolation, lobby/matchmaking, team deathmatch, health regeneration, respawn, rematch voting, and a complete UI suite.

Godot 4.6 GDScript ENet UDP Forward Plus GL Compatibility Commercial

🌐 Server-Authoritative Networking

Server validates every shot, performs hitscan raycasts, applies damage, and tracks scores. Clients never apply damage directly.

⏱️ Clock Sync & Interpolation

NTP-style clock synchronization and RTT measurement with transform snapshot interpolation at 20 Hz for smooth remote player movement.

🏃‍♂️ Lobby & Matchmaking

Server lobby allocation (up to 4 concurrent lobbies, 12 max players), lobby lock when full, map load handshake, and match start synchronization.

🔫 Team Deathmatch

Score-limit win condition, timed match, team assignment (Blue/Red), per-team spawn points, kill feed, and scoreboard.

🔄 Rematch System

End-of-match results screen with rematch voting. Original-roster rematch sessions automatically recreate replacement lobbies.

🖼️ Complete UI Suite

Login/profile creation, main menu, matchmaking UI, match HUD (health, ammo, ping, kill feed), results screen, and pause menu.

📋 What's Included

Two standalone Godot projects: Tps Client/ and Tps Server/. Each has its own project.godot, scenes, resources, and res:// namespace. No external backend, matchmaking service, or cloud backend required.

Quick Start

Starting the Dedicated Server

From the Godot editor, open Tps Server and run the project. main.tscn is the configured main scene.

From the command line:

# Windows (PowerShell)
godot --path "Tps Server" --headless

# Custom port
godot --path "Tps Server" --headless --port 7777

# Custom max players
godot --path "Tps Server" --headless --max-players 12

Server configuration can also be overridden via environment variables: SERVER_PORT, SERVER_MAX_PLAYERS.

✅ Success Indicator

You should see in the console:

SERVER LISTENING | UDP PORT: 7777 | MAX CONNECTIONS: 12

Starting the Client

Open Tps Client in Godot and run the project. The client boots to the Login Screen, then the Main Menu.

For local testing, the client defaults to connecting to 127.0.0.1:7777, so run the server on the same machine.

Testing Multiplayer (2 Clients)

  1. Start the server (Tps Server, headless or editor).
  2. Start at least two clients (Tps Client). You can run two editor instances, or one exported client plus one editor client.
  3. On each client: Enter a player name at the login screen, continue to the main menu, and press Play to enter matchmaking.
  4. When the lobby fills (max 2 players in the default tdm_1v1 config), the server locks the lobby, loads the map, and starts the match.
  5. Play: Move, aim, shoot. Hits are server-authoritative. Watch the kill feed, scoreboard, and health bar.
  6. End of match: When the score limit or timer is reached, the results screen appears. Players can vote for a rematch.

RPC Naming Convention

  • c_* (client → server): e.g., c_fire_hitscan, c_try_connect_client_to_lobby
  • s_* (server → client): e.g., s_spawn_player, s_match_timer
  • any_peer RPCs can be called by any peer; authority RPCs are server-only.

📐 Key Design Decision: Movement is Client-Authoritative

The client sends its own transform snapshots to the server, which mirrors them for other clients. The server does not simulate client movement. This means movement feels responsive but is theoretically exploitable. Hit registration, however, is fully server-authoritative.

Networking & Multiplayer

The client and server communicate over ENet UDP using Godot's MultiplayerAPI and RPC system.

Connection Flow

  1. Client creates an ENetMultiplayerPeer and connects to the server IP:port.
  2. Server accepts the peer, adds it to idle_clients (eligible for matchmaking).
  3. Client sends matchmaking request (c_try_connect_client_to_lobby) with UID, name, and cosmetics.
  4. Server places the client in a lobby. When the lobby is full, it locks and starts the match.
  5. Clients load the map, report readiness, and the server spawns players.

Clock Synchronization

The client sends clock probes (c_clock_probe) to the server. The server replies (s_clock_probe_response) with receive/send timestamps. The client calculates RTT and server offset using an NTP-style midpoint calculation:

# NTP-style midpoint offset estimation:
# offset = ((server_received - client_sent) + (server_sent - client_received)) / 2

Transform Snapshot Interpolation

The server broadcasts transform snapshots at 20 Hz (SNAPSHOT_INTERVAL = 0.05). Each snapshot includes position and visual rotation. Clients interpolate between snapshots for smooth remote-player movement.

# Server broadcasts every SNAPSHOT_INTERVAL
func broadcast_transform_snapshots() -> void:
    var snapshots: Dictionary = {}
    for client_key in clients_data.keys():
        var character := get_player_character(int(client_key))
        if character == null: continue
        var network_transform := character.get_node_or_null("NetworkTransform") as NetworkTransform
        if network_transform == null: continue
        snapshots[player_id] = {
            "position": network_transform.target_position,
            "rotation": network_transform.target_visual_rotation
        }
    s_transform_snapshots.rpc_id(int(client_key), snapshots, snapshot_sequence, server_time_usec)

RPC Reliability

  • Reliable: Critical messages (lobby, match start, fire requests, damage)
  • Unreliable: Match timer (20 Hz timer updates)
  • Unreliable Ordered: Transform snapshots (20 Hz position updates)

Authority Boundaries

  • Server owns: Combat, damage, health, scores, match clock, team assignment, spawning, respawning.
  • Client owns: Local movement, input, animation, camera, weapon prediction effects.

⚠️ Known Limitation

Client-supplied fire origin/direction is not validated against the shooter's actual position. A malicious client could shoot from arbitrary positions. This is documented as a future security task.

Tps Server/features/combat/hitscan_combat_service.gd
func handle_fire_request(
    shooter_id: int,
    origin: Vector3,
    direction: Vector3,
    weapon_id: String
) -> void:
    # Validation: match running, shooter in lobby, alive, weapon equipped
    if not lobby.match_running or not lobby.clients_data.has(shooter_id):
        return
    
    var shooter := lobby.get_player_character(shooter_id)
    var network_health := shooter.get_node_or_null("NetworkHealth") as NetworkHealth
    if network_health == null or network_health.is_dead:
        return

    # Fire rate enforcement
    var shot_interval := 1.0 / weapon_data.fire_rate
    if current_time - last_shot < shot_interval:
        return

    last_shot_times[shooter_id] = current_time
    
    # Authoritative raycast
    var query := PhysicsRayQueryParameters3D.create(
        origin,
        origin + direction.normalized() * weapon_data.range
    )
    # ... raycast logic, hit-zone detection, damage application
    
    # Damage with hit-zone and range multipliers
    var damage_multiplier := 1.0
    match hit_zone:
        "legs": damage_multiplier = 0.3
        "torso": damage_multiplier = 1.0
        "head": damage_multiplier = 4.0
    
    var actual_damage := weapon_data.damage * (1.0 - range_ratio * 0.5) * damage_multiplier
    target_health.health = max(target_health.health - actual_damage, 0.0)

Health & Damage

  • Hit Zones: Head (4×), Torso (1×), Legs (0.3)
  • Range Falloff: Damage decreases with distance (up to 50% reduction at max range)
  • Spawn Invincibility: Newly spawned players are invincible for 5 seconds
  • Health Regeneration: Server-owned, begins 3 seconds after damage, restores 10 HP/second

Match Lifecycle

States

  • IDLE: Waiting for players
  • LOCKED: Full / loading map
  • GAME: Match in progress

Flow

  1. Client requests matchmaking (c_try_connect_client_to_lobby).
  2. Server places client in lobby, tracks readiness (c_lock_client).
  3. When all clients ready, server loads map (s_start_loading_map).
  4. Clients load map, report ready (c_map_ready).
  5. Server spawns players, starts match timer (s_start_match).
  6. Match runs until score limit or time expires.
  7. Server ends match (end_match), shows results, offers rematch.

Rematch Voting

After match end, the server creates a rematch session from the original roster. All original players must vote. When everyone votes, a replacement lobby is created.

Tps Server/features/rematch/server_rematch_coordinator.gd
func handle_request(client_id: int, session_id: String) -> void:
    if not sessions.has(session_id): return
    var session: Dictionary = sessions[session_id]
    var player_ids: Array = session["player_ids"]
    if not player_ids.has(client_id): return
    
    var requested: Dictionary = session["requested"]
    if requested.has(client_id): return  # No duplicate votes
    
    requested[client_id] = true
    
    if requested.size() >= player_ids.size():
        start_session(session_id)  # All voted - create replacement lobby

Disconnect Errors Explained

⚠️ Non-Game-Breaking Console Errors

When a player disconnects during or after a match, you may see messages like these in the Godot console:

E   get_node: Node not found: "Server/<lobby_id>/<peer_id>/Player/MultiplayerSynchronizer"
E   get_cached_object: Failed to get cached node from peer <peer_id> with cache ID 3.

These errors can appear on the server, on remaining clients, or on both, and they may repeat every frame for a few seconds after the disconnect.

This is non-game-breaking. Match results, scoring, rematches, and reconnection all work normally.

Why It Happens

Godot's MultiplayerAPI maintains a scene cache mapping (peer_id, cache_id) → node for every node with a MultiplayerSynchronizer/HealthSynchronizer.

When a player disconnects:

  1. Their player character node (with synchronizers) is removed from the scene tree.
  2. Godot's MultiplayerAPI scene cache may still hold a reference to those synchronizer nodes, keyed by the departed peer's ID.
  3. When Godot processes the disconnect, or when remaining players continue sending/receiving snapshots, the engine looks up that peer ID in its cache — but the node has already been freed.
  4. The engine reports get_cached_object and get_node errors.

What's Been Done to Mitigate

  • Authority release before free: Before any player node is freed, the server explicitly transfers MultiplayerSynchronizer authority back to the server (peer 1) and sets visibility to false for all remaining peers.
  • queue_free() instead of call_deferred("queue_free"): queue_free() removes the node at end of frame, giving MultiplayerAPI one final frame to clean up its cache.
  • Lobby kept alive until peers disconnect: After match end, the lobby stays alive until all clients disconnect, rather than being freed immediately while peers are still connected.
  • Client-side authority release: Client s_player_left_match and request_leave_to_main_menu also release synchronizer authority before freeing.

If errors persist after these mitigations, check for any get_node() (not get_node_or_null()) calls targeting player synchronizers after disconnect.
