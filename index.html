Godot TPS Multiplayer Template

A commercial-grade, client-server multiplayer template for third-person shooters, built with Godot 4.6. Includes a dedicated server project, authoritative hit validation, transform snapshot interpolation, lobby/matchmaking, team deathmatch, health regeneration, respawn, rematch voting, and a complete UI suite.

Godot 4.6 GDScript ENet UDP Forward Plus GL Compatibility Commercial

🌐 Server-Authoritative Networking

Server validates every shot, performs hitscan raycasts, applies damage, and tracks scores. Clients never apply damage directly.

⏱️ Clock Sync & Interpolation

NTP-style clock synchronization and RTT measurement with transform snapshot interpolation at 20 Hz for smooth remote player movement.

🏃‍♂️ Lobby & Matchmaking

Server lobby allocation (up to 4 concurrent lobbies, 12 max players), lobby lock when full, map load handshake, and match start synchronization.

🔫 Team Deathmatch

Score-limit win condition, timed match, team assignment (Blue/Red), per-team spawn points, kill feed, and scoreboard.

🔄 Rematch System

End-of-match results screen with rematch voting. Original-roster rematch sessions automatically recreate replacement lobbies.

🖼️ Complete UI Suite

Login/profile creation, main menu, matchmaking UI, match HUD (health, ammo, ping, kill feed), results screen, and pause menu.

📋 What's Included

Two standalone Godot projects: Tps Client/ and Tps Server/. Each has its own project.godot, scenes, resources, and res:// namespace. No external backend, matchmaking service, or cloud backend required.

Quick Start

Starting the Dedicated Server

From the Godot editor, open Tps Server and run the project. main.tscn is the configured main scene.

From the command line:

# Windows (PowerShell)
godot --path "Tps Server" --headless

# Custom port
godot --path "Tps Server" --headless --port 7777

# Custom max players
godot --path "Tps Server" --headless --max-players 12

Server configuration can also be overridden via environment variables: SERVER_PORT, SERVER_MAX_PLAYERS.

✅ Success Indicator

You should see in the console:

SERVER LISTENING | UDP PORT: 7777 | MAX CONNECTIONS: 12

Starting the Client

Open Tps Client in Godot and run the project. The client boots to the Login Screen, then the Main Menu.

For local testing, the client defaults to connecting to 127.0.0.1:7777, so run the server on the same machine.

Testing Multiplayer (2 Clients)

  1. Start the server (Tps Server, headless or editor).
  2. Start at least two clients (Tps Client). You can run two editor instances, or one exported client plus one editor client.
  3. On each client: Enter a player name at the login screen, continue to the main menu, and press Play to enter matchmaking.
  4. When the lobby fills (max 2 players in the default tdm_1v1 config), the server locks the lobby, loads the map, and starts the match.
  5. Play: Move, aim, shoot. Hits are server-authoritative. Watch the kill feed, scoreboard, and health bar.
  6. End of match: When the score limit or timer is reached, the results screen appears. Players can vote for a rematch.

RPC Naming Convention

  • c_* (client → server): e.g., c_fire_hitscan, c_try_connect_client_to_lobby
  • s_* (server → client): e.g., s_spawn_player, s_match_timer
  • any_peer RPCs can be called by any peer; authority RPCs are server-only.

📐 Key Design Decision: Movement is Client-Authoritative

The client sends its own transform snapshots to the server, which mirrors them for other clients. The server does not simulate client movement. This means movement feels responsive but is theoretically exploitable. Hit registration, however, is fully server-authoritative.

Server Lobby — Component Split

The server Lobby (features/lobby/lobby.gd) is now a coordinator. It owns and delegates to:

  • LobbyPlayerManager (features/lobby/lobby_player_manager.gd): player registration/removal, client data, roster, teams, kills, spawn-invincibility timing, ready clients, scoreboard data.
  • LobbyMatchClock (features/match/lobby_match_clock.gd): match timer, running/ended state, 250 ms timer broadcasts.
  • MatchPlayerSpawner (features/players/match_player_spawner.gd): team assignment, spawn points, spawning, respawning.
  • HitscanCombatService (features/combat/hitscan_combat_service.gd): authoritative fire validation, raycast, damage, kills; weapon lookups via WeaponRegistry.
  • MatchResult (features/match/match_result.gd): completed-match outcome data delivered through the existing s_match_time_expired RPC.
  • ServerRematchCoordinator (features/rematch/server_rematch_coordinator.gd): rematch voting and replacement-lobby creation.

No RPC names, annotations, or payload layouts changed as a result of the split.

Network Contract (Do Not Break Lightly)

The following are part of the current client-server network contract. Changing them requires coordinated changes on both projects:

  • RPC names and annotations: c_* (client→server) and s_* (server→client), with any_peer / authority and reliable / unreliable / unreliable_ordered modes.
  • Player scene node paths: "Player", "NetworkTransform", "HealthSynchronizer", "NetworkHealth", "PlayerReplication", "PlayerAnimator", "Col".
  • Multiplayer authority: Local player character gets authority from its client ID; HealthSynchronizer gets authority from peer ID 1 (server).
  • Lobby scene tree: Server Lobby node contains Map and child player nodes named by client_id (e.g., "1", "2").
  • Match config: MatchConfig Resource with mode_id, rules_script, map_id, and match settings.

  1. Connection: The client client_server.gd creates an ENet client and connects to the server. The server dedicated_server.gd creates an ENet server host and accepts peers.
  2. Matchmaking: The client sends c_try_connect_client_to_lobby with UID/name/cosmetics. The server places the client into a lobby (or creates one). When the lobby is full, it locks and tells clients to load the map.
  3. Loading: The server Lobby instantiates the server map, tells all clients to load their map (s_start_loading_map), clients reply c_map_ready. When all are ready, players spawn.
  4. Spawning: The server MatchPlayerSpawner assigns teams and spawn points, instantiates PlayerServer bodies, and calls s_spawn_player on each client. The client ClientLobby uses PlayerPresentationFactory to instantiate local or remote player scenes.
  5. In match: Clients send input locally. The local PlayerController sends c_fire_hitscan (origin, direction, weapon_id) when shooting. The server HitscanCombatService validates, raycasts, applies damage, and broadcasts results (s_weapon_fired, s_weapon_impact, s_hit_confirmed, s_kill_registered).
  6. Synchronization: The server broadcasts transform snapshots (s_transform_snapshots) at 20 Hz. Remote clients interpolate between snapshots for smooth movement.
  7. Match end: The server ends the match on score limit or time expiry, shows results, and may create a rematch session.
  8. Rematch: Clients vote via c_request_rematch. The server ServerRematchCoordinator collects votes; when all original players agree, it creates a new lobby with the same roster.

Authority and Validation Notes

  • Player movement/animation: Client-authoritative for the local player; transform snapshots reconcile remote players.
  • Health: Server-owned. The server HitscanCombatService applies damage; NetworkHealth is synchronized to clients via HealthSynchronizer with server authority (peer ID 1).
  • Combat: Server-validated. The server checks fire rate, weapon equipped, alive state, and performs the raycast.
  • Match lifecycle: Server-owned (match clock, score limit, end condition, spawn/respawn).
  • No client-side hit validation: The client trusts the server's hit/damage results.

Adding a Game Mode

Server match configuration lives in Tps Server/features/match/data/. A MatchConfig Resource contains a stable mode_id and a rules_script reference to a MatchRules implementation.

  1. Add a MatchRules subclass in Tps Server/features/match/ for scoring and winner logic.
  2. Add a .tres MatchConfig with the rules script and mode settings.
  3. Select that Resource in match_config in Tps Server/autoload/dedicated_server.gd.
  4. Add client presentation only when the mode needs it; keep gameplay decisions on the server.

Networking & Multiplayer

The client and server communicate over ENet UDP using Godot's MultiplayerAPI and RPC system.

Connection Flow

  1. Client creates an ENetMultiplayerPeer and connects to the server IP:port.
  2. Server accepts the peer, adds it to idle_clients (eligible for matchmaking).
  3. Client sends matchmaking request (c_try_connect_client_to_lobby) with UID, name, and cosmetics.
  4. Server places the client in a lobby. When the lobby is full, it locks and starts the match.
  5. Clients load the map, report readiness, and the server spawns players.

Clock Synchronization

The client sends clock probes (c_clock_probe) to the server. The server replies (s_clock_probe_response) with receive/send timestamps. The client calculates RTT and server offset using an NTP-style midpoint calculation:

# NTP-style midpoint offset estimation:
# offset = ((server_received - client_sent) + (server_sent - client_received)) / 2

Transform Snapshot Interpolation

The server broadcasts transform snapshots at 20 Hz (SNAPSHOT_INTERVAL = 0.05). Each snapshot includes position and visual rotation. Clients interpolate between snapshots for smooth remote-player movement.

# Server broadcasts every SNAPSHOT_INTERVAL
func broadcast_transform_snapshots() -> void:
    var snapshots: Dictionary = {}
    for client_key in clients_data.keys():
        var character := get_player_character(int(client_key))
        if character == null: continue
        var network_transform := character.get_node_or_null("NetworkTransform") as NetworkTransform
        if network_transform == null: continue
        snapshots[player_id] = {
            "position": network_transform.target_position,
            "rotation": network_transform.target_visual_rotation
        }
    s_transform_snapshots.rpc_id(int(client_key), snapshots, snapshot_sequence, server_time_usec)

RPC Reliability

  • Reliable: Critical messages (lobby, match start, fire requests, damage)
  • Unreliable: Match timer (250 ms timer updates)
  • Unreliable Ordered: Transform snapshots (20 Hz position updates)

Authority Boundaries

  • Server owns: Combat, damage, health, scores, match clock, team assignment, spawning, respawning.
  • Client owns: Local movement, input, animation, camera, weapon prediction effects.

⚠️ Known Limitation

Client-supplied fire origin/direction is not validated against the shooter's actual position. A malicious client could shoot from arbitrary positions. This is documented as a future security task.

Multiplayer Authority

Player Authority

When a player is spawned, the client PlayerPresentationFactory calls:

character.set_multiplayer_authority(client_id, true)

This gives the owning client authority over its own PlayerController. The server (MatchPlayerSpawner) does the same for PlayerServer bodies. Remote player instances have no authority on any client except their owner.

Health Authority

The HealthSynchronizer on each player is assigned authority to peer ID 1 (the server). This means only the server can write to NetworkHealth.health / is_dead; clients receive those changes via synchronization. The client PlayerHealth script also calls set_multiplayer_authority(1) in _ready() to enforce this.

RPC Authority

@rpc("authority", ...) functions can only be invoked by the server. @rpc("any_peer", ...) functions can be invoked by any connected peer. The server validates all c_* requests before acting.

Assumptions & Edge Cases

  • Default port 7777: Both client and server default to UDP 7777. If you change one, change the other (or pass matching CLI/env overrides).
  • No NAT punchthrough: Clients must reach the server's IP directly. For internet play, port forwarding is required.
  • Max 4 lobbies, 12 players: The default server caps at 4 concurrent lobbies and 12 total players. The default match config (tdm_1v1.tres) uses max_players=2.
  • Lobby IDs are instance IDs: Server lobby names are str(get_instance_id()), which are stable for a server session but not meaningful across restarts.
  • Transform snapshots are unreliable_ordered: Snapshot loss is tolerated; clients interpolate from available snapshots rather than waiting for retransmission.
  • Match timer is unreliable: s_match_timer is sent unreliably every 250 ms; occasional missed ticks are acceptable.

Gameplay & Combat

Weapons

Two weapons ship by default: AK47 (rifle) and MP5 (submachine gun). Each project has separate WeaponData resources, and the weapon_id must match exactly between the client and server copies.

The server looks up weapons through its WeaponCatalog / WeaponRegistry rather than hard-coded paths. When a client sends a fire request, the HitscanCombatService validates that the weapon is registered; unknown weapon IDs return null and the request is rejected — no default stats are invented.

Health & Damage

  • Hit Zones: Head (4×), Torso (1×), Legs (0.3)
  • Range Falloff: Damage decreases with distance (up to 50% reduction at max range)
  • Spawn Invincibility: Newly spawned players are invincible for spawn_invincibility_time (default 5 seconds, from MatchConfig)
  • Fire-Rate Enforcement: The server validates a 1/fire_rate interval between shots
  • No Spread: Hitscan is a pure ray from origin along direction

Team Assignment

Teams are assigned alternately (Blue = 0, Red = 1) during spawning. Spawn points are selected by name prefix ("Blue..." / "Red...").

See Adding Weapons for the full authoring workflow (creating server/client WeaponData, registering in the catalog, and assigning loadout slots).

Adding Maps

Map selection is data-driven. The server selects a map via MatchConfig.map_id, which references a MapData entry in the server MapCatalog. Clients receive the map_id via the s_start_loading_map RPC and load the matching client map from their own MapCatalog.

Each map needs two MapData resources — one in each project — with the same map_id:

Map Loading Flow

  1. Server Lobby.setup_match() resolves map_data from the catalog using config.map_id.
  2. Server Lobby.start_loading_map() instantiates map_data.server_map_scene and sends s_start_loading_map(map_id) to all clients.
  3. Client ClientLobby.s_start_loading_map(map_id) looks up map_data.client_map_scene from its catalog and instantiates it.
  4. Client replies with c_map_ready when loaded.
  5. Server spawns players and starts the match.

Adding a New Game Mode

Adding a new game mode requires both a MatchRules subclass (code) and a MatchConfig resource (data).

  1. Create a MatchRules subclass: Implement on_player_killed(), get_winner_team(), and optionally can_respawn() / reset_match().
  2. Create a MatchConfig .tres: Reference your rules script and set mode settings.
  3. Assign in the editor: Set match_config in dedicated_server.gd.
  4. Add client presentation: Only when the mode needs a different HUD or results screen; keep gameplay decisions on the server.

📊 Configurable vs Code-Required

Resource-only (no code): Score limit, match duration, max players, team count, respawn settings, map selection.

Requires GDScript: New scoring logic, new win conditions, new spawn rules, new match-end conditions.

Match Lifecycle

StateDescription
IDLEWaiting for players
LOCKEDFull / loading map
GAMEMatch in progress
  1. Client requests matchmaking (c_try_connect_client_to_lobby).
  2. Server places client in lobby, tracks readiness (c_lock_client).
  3. When all clients ready, server loads map (s_start_loading_map).
  4. Clients load map, report ready (c_map_ready).
  5. Server spawns players, starts match timer (s_start_match).
  6. Match runs until score limit or time expires.
  7. Server ends match (end_match), shows results, offers rematch.

Rematch Voting

After match end, the server creates a rematch session from the original roster. All original players must vote. When everyone votes, a replacement lobby is created with the same match config.

  • Requires: All original roster members connected and voted.
  • Cleared if: A player leaves before voting (clear_rematch_session).
  • 1v1: If one player leaves, the match ends immediately — no rematch session created.

Adding a New Animation

  1. Open the player scene (player_local.tscn or player_remote.tscn) and edit the AnimationTree assigned to anim_tree.
  2. Add your animation to the relevant state machine or blend tree in the editor.
  3. Expose a parameter: condition (bool), blend parameter (float/Vector2), or one-shot request.
  4. Add a script method in PlayerAnimationController that sets the parameter via anim_tree.set("parameters/...", value) or travels via weapon_state_machine.travel("StateName").
  5. Wire the caller: player_local.gd for movement, weapon_system.gd for weapon actions; add replicated fields to NetworkState if remote players must mirror them.

AnimationNodeOneShot

AnimationNodeOneShot is already used in this project: the DeathOneShot node plays the death animation when a player dies (ONE_SHOT_REQUEST_FIRE) and is aborted on respawn (ONE_SHOT_REQUEST_ABORT). It is not currently used for reload or fire reactions — reload uses the Weapon_Reload condition in WeaponsStateMachine, and weapon fire plays through a separate AnimationPlayer on the weapon instance.

To add a new one-shot (e.g., reload reaction):

  1. Add an AnimationNodeOneShot node to the AnimationTree (e.g., named ReloadOneShot).
  2. Expose a request parameter.
  3. Fire it from a new PlayerAnimationController method.

Animation Conflicts

⚠️ Upper-Body Filter During Airborne States

The upper-body blend filter (BlendBody.filter_enabled) must be disabled during jumping/falling/landing (set_airborne_filter_override / begin_landing_filter), otherwise aim animations distort full-body airborne movement. The landing filter lasts landing_filter_duration (exported, default 0.15 s).

Troubleshooting

This document covers common setup errors, networking problems, missing resources, and other issues. Solutions are provided based on the documented implementation.

Setup and Project Issues

Godot Version Mismatch

Symptom: The project fails to open or reports an incompatible engine version.

Cause: Both project.godot files declare config_version=5 and config/features=PackedStringArray("4.6", ...), requiring Godot 4.6.

Solution: Install Godot 4.6. Do not attempt to open with Godot 4.x earlier than 4.6 or Godot 5 without first verifying compatibility.

Missing Main Scene

Symptom: The project starts but shows an empty viewport or the editor's default scene.

Cause: run/main_scene in project.godot points to a UID (uid://...) that may not resolve if the scene was moved or the UID cache is stale.

Solution: In the Godot editor, set Project > Project Settings > Application > Run > Main Scene to:

  • Client: res://game/main_game.tscn
  • Server: res://game/main.tscn

Missing Autoload Nodes

Symptom: push_error("Server not found!"), push_error("GameServer not found while ending match."), or similar errors at runtime.

Cause: An autoload script listed in [autoload] is missing, renamed, or its add_to_group call didn't run.

Solution: Verify [autoload] entries in project.godot:

  • Client: Server="*res://autoload/client_server.gd", GameState="*res://autoload/game_state.gd", RematchManager="*res://features/rematch/rematch_manager.gd".
  • Server: Server="*res://autoload/dedicated_server.gd", RematchManager="*res://features/rematch/rematch_manager.gd".

Ensure the scripts call add_to_group(...) as expected (ClientServer → "ClientServer", dedicated_server.gd → "GameServer", rematch managers → "RematchManager").

Missing Match Config

Symptom: Server logs "Cannot start rematch: server MatchConfig is missing." or "Invalid match configuration: rules_script must extend MatchRules."

Cause: dedicated_server.gd's match_config export points to a missing or invalid .tres, or the rules_script does not extend MatchRules.

Solution: Verify Tps Server/features/match/data/tdm_1v1.tres exists and its rules_script references res://features/match/tdm_rules.gd. Confirm tdm_rules.gd extends MatchRules. Assign the config in dedicated_server.gd's match_config export.

Networking Issues

Client Cannot Connect to Server

Symptom: match_making_ui.gd shows "No Internet" or client_cant_connect_to_lobby; server logs no peer connection.

Possible causes (in order):

  1. Server is not running.
  2. Client IP_ADDRESS/PORT does not match the server's listen address/port.
  3. Firewall blocking UDP 7777.
  4. Server bound to a specific interface the client cannot reach.

Solutions:

  • Confirm the server process is running and logs "SERVER LISTENING | UDP PORT: 7777".
  • Confirm both client and server use the same port (default 7777). Override with --port= on both or SERVER_PORT env var.
  • For LAN play, set the client IP_ADDRESS to the server's local IP via --ip=192.168.x.x or SERVER_IP.
  • For internet play, forward UDP port 7777 on the server's router and give clients the public IP.
  • Ensure both projects use Godot 4.6 (ENet behavior differs across versions).

Lobby Will Not Fill / Match Will Not Start

Symptom: Clients connect but the lobby never locks; "Match Making: 1/2" stays stuck.

Possible causes:

  1. Not enough clients connected (default max_players = 2).
  2. One or more clients did not call c_lock_client (client ready).
  3. One or more clients did not call c_map_ready (map loaded).
  4. Server MAX_LOBBIES (4) is reached and no lobby has room.

Solutions:

  • Start the number of clients required by match_config.max_players.
  • Check the server console for "Client %d is ready" messages.
  • Confirm the client map (test_map.tscn) loads without errors on each client.
  • Check lobby_clients_updated signal on the client UI to see if population is advancing.

Hits Do Not Register

Symptom: The client shoots, local effects play, but no damage appears on the target and no kill feed entry.

Possible causes (all enforced server-side in HitscanCombatService.handle_fire_request):

  1. Match is not running (lobby.match_running == false).
  2. Shooter is dead (network_health.is_dead == true).
  3. Shooter's weapon_equipped is false or weapon_id does not match the fired weapon.
  4. Fire-rate limit not met (last_shot_times enforces 1/fire_rate between shots).
  5. weapon_data not found in the server's WeaponRegistry.
  6. The raycast did not hit a player in this lobby (collision mask, wrong layer, or another lobby's collider blocked the ray).
  7. Target is in the spawn invincibility window (spawn_invincibility_time).

Solutions:

  • Confirm the server logs "HIT ZONE" or "SCORE" on hits.
  • Confirm the weapon is registered in HitscanCombatService.weapon_registry (ak47_data.tres, mp5_data.tres are registered by default).
  • Confirm the shooter is alive and has the weapon equipped.
  • Check spawn_invincibility_time if shooting immediately after spawn.

Remote Players Not Visible / Not Moving

Symptom: Other players' characters are missing or frozen.

Possible causes:

  1. s_spawn_player was not received (lobby not fully ready).
  2. MultiplayerSynchronizer visibility not set for the peer (_configure_match_visibility on the server sets visibility per lobby peer).
  3. Client ClientLobby not added to group "ClientLobby" (snapshot receiver can't find it).
  4. Clock sync not established (get_estimated_server_time_usec() returns -1), so interpolation has no render time.

Solutions:

  • Confirm all clients call c_map_ready so the server spawns players.
  • Confirm server MatchPlayerSpawner._configure_match_visibility sets set_visibility_for(peer_id, true) for each lobby peer.
  • Confirm client ClientLobby._ready() calls add_to_group("ClientLobby").
  • Wait a few seconds for clock probes to establish; check the ping display on the HUD.

Missing Resources

Weapon Data Missing

Symptom: push_warning("PlayerRemote: Weapon ID not found: ...") or server ignores fire requests.

Cause: A weapon_id used by the client has no matching WeaponData in the server's WeaponRegistry, or the client WeaponData.weapon_scene is null.

Solution: Add the weapon .tres to both projects' features/weapons/data/, register it in the server's WeaponCatalog (see HitscanCombatService.setup), and assign weapon_scene/tracer_scene on the client.

Missing Scenes

Symptom: Invalid type in function 'instantiate' in base 'PackedScene'. or a null scene reference.

Cause: A PackedScene export is empty in the editor, or the .tscn file was moved/deleted.

Solution: In the editor, open each WeaponData, MatchConfig, and player scene and reassign any empty PackedScene or Script exports. Verify res://features/weapons/scenes/ak_47_scene.tscn, mp5_scene.tscn, res://features/players/local/player_local.tscn, res://features/players/remote/player_remote.tscn, and res://features/players/player_server.tscn exist.

Map Not Found

Symptom: Map .tscn returns null when loading.

Cause: Map .tscn was moved or renamed, or map_id doesn't match a MapData entry in the catalog.

Solution:

  • Verify the MapData resource exists in both projects' features/match/data/ with the correct map_id.
  • Verify the MapCatalog references the MapData resource.
  • Verify the MatchConfig.map_id matches the map_id in the catalog.

Match and Gameplay Issues

Match Timer Not Updating

Symptom: The HUD timer stays at 00:00 or never counts down.

Cause: s_match_timer is an unreliable RPC sent every 250 ms by LobbyMatchClock.update. Individual packets may be lost, but the timer should still update regularly.

Solution: Confirm match_clock.start(duration) was called (server logs "MATCH CREATED"). Check match_running on the server Lobby.

Respawn Not Working

Symptom: Pressing respawn does nothing after death.

Cause: c_request_respawn is only honored if network_health.is_dead is true on the server's player character. If the server's health state hasn't synchronized, the request is ignored.

Solution: Confirm the server applied damage and set is_dead = true. Confirm respawn_enabled is true in MatchConfig. Check MatchPlayerSpawner.respawn_player logic.

1v1 Match Ends When One Player Leaves

Symptom: In a 2-player match, one player disconnecting ends the match immediately with the other as winner.

Cause: This is intentional behavior in Lobby.handle_player_leaving for max_players == 2 (1v1).

Solution: Not a bug. To allow larger matches to continue after a disconnect, increase max_players in MatchConfig and add more spawn points.

Rematch Vote Not Starting

Symptom: Players click Rematch but no new lobby is created.

Cause: ServerRematchCoordinator.start_session requires all original roster members to be connected and to have voted (requested.size() >= player_ids.size()). If one player left or didn't vote, the rematch won't start.

Solution: Confirm all original players are still connected. The session is cleared if a player leaves (clear_rematch_session).

Disconnect Errors Explained

ℹ️ Engine Console Messages on Disconnect

When a player disconnects during or after a match, you may see messages like these in the Godot console:

E   get_node: Node not found: "Server/<lobby_id>/<peer_id>/Player/MultiplayerSynchronizer"
E   get_cached_object: Failed to get cached node from peer <peer_id> with cache ID 3.

These errors can appear on the server, on remaining clients, or on both, and they may repeat for several seconds after the disconnect.

What Causes These Errors

These messages come from a known Godot Engine issue (godotengine/godot#101847), which affects Godot's MultiplayerAPI scene cache. When a replicated node (a player character with MultiplayerSynchronizer or HealthSynchronizer) is freed, the engine's internal scene cache can retain a stale entry keyed by the departed peer's ID. Later lookups during disconnect processing or ongoing replication (such as transform snapshots) fail with get_cached_object / get_node errors.

This is an engine-side issue, not a problem with your game logic. It has been reported across Godot 4.3 through 4.6.2 and remains open in the engine issue tracker.

What This Template Does

The template applies the standard mitigations for this class of issue:

  • Authority release before free: Before a player node is freed, the server returns MultiplayerSynchronizer/HealthSynchronizer authority to peer ID 1 (the server) and disables visibility for all remaining peers. This tells MultiplayerAPI to release its scene-cache references before the node is destroyed.
  • Deferred deletion: Player nodes and empty lobbies are freed with call_deferred("queue_free") rather than synchronously, giving MultiplayerAPI time to finish processing pending replication.

What to Expect

The console messages are engine scene-cache noise. They do not indicate a crash, data corruption, or broken match logic in themselves. Whether the match continues correctly after a disconnect depends on the match type:

  • Team matches: Remaining players continue normally; the departing player's character is removed and the match carries on.
  • 1v1 matches: If one player leaves, the match ends with the remaining player as the winner.

If your match results, scoring, rematches, and reconnection all work correctly, the errors can be treated as engine console noise. This description is based on code inspection; if the message persists despite the mitigations above, it is a known engine behavior rather than a template bug.

Troubleshooting

  • Prefer get_node_or_null() (not get_node()) for player synchronizer paths after a disconnect.
  • Do not replace call_deferred("queue_free") with immediate queue_free() based on this error alone; immediate deletion can interrupt pending replication.
